# ADR-0003 — فرایند تصویب و فعال‌سازی Provider

- وضعیت: پذیرفته‌شده برای استفاده فرایندی
- نسخه: `1.0.0`
- تاریخ تصویب: `2026-11-24`
- مالک تصمیم: Platform Governance
- الزام مرتبط: `SEC-002`
- قرارداد مرجع: `docs/contracts/S01-W04.json` نسخه `1.0.0`
- مدل عملیاتی: `docs/decisions/provider-approval-workflow.v1.json`

## مسئله

قانون محل داده کودک، رضایت سرپرست و انتخاب درگاه پرداخت، پیامک، فایل، دستگاه حضور و اتصال مالی مدرسه به تصمیم حقوقی، امنیتی، مالی و فنی وابسته است. هنوز حوزه قضایی، متن رضایت، Provider، بودجه، قرارداد و POC واقعی تصویب نشده‌اند. فعال‌سازی بر پایه نام یک Provider یا تصمیم یک نفر می‌تواند داده کودک، پول، Secret و صحت مالی را در معرض خطر قرار دهد.

## تصمیم

1. برای هر یک از هفت موضوع قرارداد `S01-W04` یک پرونده نسخه‌دار با مالک، سه نقش تصویب‌کننده، مهلت برنامه‌ریزی و فهرست evidence ایجاد می‌شود.
2. evidence خام در Git ثبت نمی‌شود؛ فقط reference مبهم، SHA-256، طبقه‌بندی، صادرکننده و زمان اعتبار نگهداری می‌شود.
3. تغییر evidence همه تصویب‌های نسخه قبلی را بی‌اعتبار می‌کند. هر سه نقش تنظیم‌شده باید همان نسخه و همان manifest را تصویب کنند.
4. پنج Provider هرکدام رکورد مستقل قرارداد، بودجه، POC، محل پردازش، Secret reference و وضعیت فعال‌سازی دارند.
5. بودجه همه Providerها فقط با نقش `finance_owner` تصویب می‌شود؛ مبلغ، ارز و دوره باید صریح باشند.
6. Secret فقط با reference به secret manager ثبت می‌شود. مقدار Secret در سند، Git، log یا approval ممنوع است.
7. deadline تنها برای هشدار و escalation است و هیچ موضوعی را خودکار تصویب نمی‌کند.
8. عبور همه Gateها فقط پرونده را `activation_requested` می‌کند. فعال‌سازی production نیازمند change مستقل، تأییدشده، قابل rollback و رسید ممیزی است.
9. تا زمان ثبت تصمیم‌های واقعی، تمام پرونده‌ها در `evidence_collecting` و تمام Providerها `denied` باقی می‌مانند.

## جریان عملیاتی

1. مالک تصمیم پرونده نسخه‌دار را باز می‌کند.
2. evidence با metadata و hash ثبت می‌شود.
3. validator کامل‌بودن manifest را کنترل می‌کند.
4. سه نقش مستقل evidence همان نسخه را بررسی و تصویب می‌کنند.
5. مقدار بیرونی تصمیم—مانند حوزه قضایی، نسخه سیاست رضایت یا مشخصات Provider—با تاریخ اثر ثبت می‌شود.
6. موتور workflow همه Gateهای حقوقی، امنیتی، قرارداد، بودجه، POC، محل پردازش و Secret reference را ارزیابی می‌کند.
7. مالک پلتفرم یک production change جداگانه درخواست می‌کند.
8. پس از approval تغییر، فعال‌سازی محدود انجام و رسید ممیزی ثبت می‌شود.

## وضعیت فعلی

- دو پرونده حریم خصوصی: evidence در حال جمع‌آوری و مقدار حقوقی هنوز ثبت نشده است.
- پنج Provider: قرارداد `unsigned`، بودجه `unapproved`، POC برابر `not_run`، محل پردازش `TBD` و فعال‌سازی `denied` است.
- هیچ Provider، کلید، endpoint یا تغییر production در این ADR فعال نشده است.

## پیامدها

- تصمیم‌ها از گفت‌وگو و فایل پراکنده به فرایند قابل‌ممیزی تبدیل می‌شوند.
- یک نقش نمی‌تواند Gate حقوقی، امنیتی و مالی را به‌تنهایی دور بزند.
- evidence منقضی یا تغییرکرده اجازه استفاده از approval قدیمی را نمی‌دهد.
- انتخاب Provider و هزینه واقعی همچنان کار بیرونی است و باید با مدرک ثبت شود.

## Rollback

این تصمیم فقط سند و مدل عملیاتی است و داده یا runtime تولیدی را تغییر نمی‌دهد. rollback با Git revert انجام می‌شود. rollback فعال‌سازی آینده باید در production change همان Provider تعریف و آزموده شود.
