# ADR-0001 — مبنای منابع و اولویت محصول

- وضعیت: پذیرفته‌شده
- نسخه: 1.0.0
- تاریخ تصویب: 2026-11-22
- مالک تصمیم: Product Architecture
- الزام مرتبط: FR-001

## مسئله

سه ورودی درباره محدوده محصول وجود دارد و نقش یکسانی ندارند: پروپوزال مهندسی ۲.۱، پروپوزال جامع و شواهد HAR. بدون ترتیب اعتبار روشن، قابلیت‌های مشاهده‌شده در سامانه مرجع می‌توانند اشتباهاً API یا تعهد MVP تلقی شوند و قابلیت‌های P2/P3 نیز وارد فروش نسخه اول شوند.

## تصمیم

1. پروپوزال مهندسی ۲.۱ مرجع قطعی مرز P0 و P1، معماری، امنیت و معیارهای نسخه اول است.
2. پروپوزال جامع مرجع حفظ پوشش قابلیت‌های P2 و P3 است؛ این قابلیت‌ها حذف نمی‌شوند، اما تعهد MVP نیستند.
3. HAR فقط شاهد وجود حوزه‌ها و عملیات سامانه مرجع است. HAR قرارداد API، اثبات رفتار انتهابه‌انتها یا مجوز کپی ساختار داخلی نیست.
4. هر تغییر اولویت نیازمند افزایش نسخه این تصمیم، ثبت دلیل، اثر روی API/داده و PR بازبینی‌شده است.
5. فروش P0 نباید P1، P2 یا P3 را وعده دهد. P1 تنها پس از عبور Gate مستقل انتشار عرضه می‌شود.

## مصوبه اولویت‌ها

| اولویت | محدوده | Gate خروج |
|---|---|---|
| P0 | هویت و نشست، Tenant و سازمان، مجوز، فیلد سفارشی محدود، پلن و پرداخت، entitlement، فایل خصوصی، Site Registry و زیردامنه | جداسازی دو Tenant، پرداخت idempotent و عدم دسترسی عمومی به فایل خصوصی |
| P1 | صفحه‌ساز و دامنه، School Core، ثبت‌نام و سرپرستی، حضور، اعلان و اتصال فقط‌خواندنی مالی | مسیر خرید تا مدرسه در staging، rollback و restore آزموده‌شده |
| P2 | LMS، تکلیف، نمره و آزمون، کلاس زنده، دوره و رویداد، CRM، فروشگاه، قرارداد، HR و گزارش‌ساز | تقاضای تجاری، بودجه و قرارداد Provider معتبر |
| P3 | حسابداری کامل، حقوق، بوفه و کیف پول، حمل‌ونقل پیشرفته، BI پیش‌بینی، OMR و AI حساس | ADR مستقل، تحلیل ROI، بررسی حقوقی و پایلوت |

## مرز Tenant و سناریوی پذیرش

یک شخص می‌تواند در دو Tenant عضویت مستقل و نقش متفاوت داشته باشد. تغییر context فقط زمانی مجاز است که عضویت فعال همان Tenant وجود داشته باشد؛ نقش Tenant قبلی هرگز حمل نمی‌شود. درخواست Tenant ثالث با خطای پایدار `TENANT_CONTEXT_MISMATCH` رد می‌شود. این قاعده از FR-001 و مرز امنیتی P0 پشتیبانی می‌کند.

## پیامدها

- اولویت‌ها قابل آزمون و قابل ردیابی شده‌اند.
- HAR نمی‌تواند به‌تنهایی endpoint یا رفتار محصول جدید ایجاد کند.
- قابلیت‌های جامع حفظ می‌شوند، اما ورود آن‌ها به P0/P1 تنها با revision رسمی ممکن است.
- قرارداد ماشین‌خوان در `product-priority-baseline.v1.json` و تست پذیرش در `tests/S01-W01/priority-baseline.test.mjs` قرار دارد.

## Rollback

این تصمیم داده عملیاتی یا migration ایجاد نمی‌کند. Rollback با revert کردن commit انجام می‌شود؛ تاریخچه نسخه قبلی باید در Git باقی بماند.
