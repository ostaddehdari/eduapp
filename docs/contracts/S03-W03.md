# S03-W03 · Access policies

| Contract | Version | Requirements |
| --- | --- | --- |
| S03-W03 | 1.0.0 | CORE-04, FR-002 |

Access makes policy decisions for a verified membership. The Gateway authenticates and routes; each resource owner binds an operation to a permission and supplies the verified tenant, organizational unit and resource. Public requests never supply an authority-bearing policy target or relationship. A live session and a valid tenant membership are both required.

## Decision order

1. Resolve the actor's selected membership in its tenant on each decision. Honor its status and expiration. A school-bound membership reaches only the exact registered organizational unit. The owner resolves school IDs into organizational unit IDs. This version does not infer access through ancestors.
2. Read roles through active role bindings in that same tenant, then intersect each binding's scope with the membership scope. Match the operation to explicit allow or deny rules. Any applicable deny wins. Missing allow denies access.
3. For a guarded read, confirm the guardian link through the School owner for the actor, child, school scope and tenant. The School owner is responsible for rejecting unverified or revoked links. The Billing owner confirms a required feature independently of the role policy. Missing or negative proof fails closed for actions that need it.
4. Merge the allowed fields only after the action passes. Project scalar owner-defined fields into a fresh response object. A child profile rule can disclose `studentId`, `displayName`, `gradeLevel` or `attendanceStatus` only when explicitly allowed. Ordinary People read projections allow `id` and `displayName`. Cursor positions are opaque and use owner-controlled keys.

Rules have an action, an `allow` or `deny` effect, an optional `verified_guardian` relationship for `school.student.read`, and an optional list of allowed fields. Denies cannot carry fields. Role administration is tenant-level only and reserved for provisioned built-in roles. The API cannot create, edit or assign a built-in role. Editors may only delegate tenant-wide permissions and fields they can grant; a conditional grant cannot be broadened to an unconditional one. Use fresh MFA for role creation, editing and assignment and for the People membership and invitation operations. An owner verifies an org unit before binding a role to it.

## HTTP contract

| Operation | Gates and outcome |
| --- | --- |
| `getMyCapabilities` | Active tenant membership. Returns effective operation and field capabilities for the active scope. Resource-specific authorization still happens at the owner. |
| `listRoles` | Tenant-level `access.role.read`; existing Gateway cursor semantics. |
| `createRole` | Tenant-level `access.role.write`, fresh MFA, delegable policy. Returns 201. |
| `updateRole` | Same creation gates with an atomic `If-Match` check. Returns the new ETag; stale versions return 412. |
| `assignRole` | Tenant-level `access.role.assign`, fresh MFA, delegable target role, active same-tenant membership and compatible branch scope. Returns 201. |
| People reads | The People owner delegates authorization and field projection before serialization. |
| School read adapter | The School owner supplies the tenant-scoped resource and its required entitlement to the Access adapter. A denied or absent resource gives the same 404. |

HTTP uses the existing operation IDs and shared Gateway error envelope. Validation is performed by the owner service. This phase introduces no public authorization event or client-driven cross-tenant lookup.

## Storage and privileges

| Data | Owner and boundary |
| --- | --- |
| `memberships`, `roles`, `role_bindings` | Access owns the PostgreSQL tables. Migration `0004-access-policy.sql` adds the bounded JSON rule list and the built-in marker to existing roles. Existing roles without explicit policy grant nothing. RLS and compound tenant references remain in effect. |
| `guardian_links` | School. Access consumes an owner-authorized relationship check. |
| `entitlements` | Billing. Access consumes an owner-authorized feature check. |
| Login and verification | IAM authenticates principals and establishes MFA freshness. Its credentials stay out of Access storage and responses. |

Only the Access runtime uses its PostgreSQL role to execute policy reads and custom role mutations. Clients and Gateway network code cannot read these tables directly. Initial built-in role bindings are trusted tenant provisioning. No unauthenticated bootstrap operation is exposed.
