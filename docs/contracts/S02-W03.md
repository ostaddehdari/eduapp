The [Gateway contract](S02-W02.json) and the [OpenAPI catalog](../../preview/api/openapi.json) define the existing HTTP surface. ## Tenant key and references

| Scope | Tables or records | Access rule |
| --- | --- | --- |
| Tenant | School, enrollment, attendance, sites, notifications and other tenant records listed in the JSON | Require a non-null UUID `tenant_id`. Apply the tenant predicate to reads and writes. Child tables including domains, page revisions, attendance revisions, message attempts and the tenant inbox carry the same key as their parent or validated event. |
| Tenant root | `tenants` | The existing UUID primary key `id` is the tenant key. Bind the generated ID after authorizing provisioning. List only tenants from verified access scopes, binding one tenant at a time. |
| Owner-private global | IAM `identities` and `sessions`, Billing `provider_events` | Limit grants to the owning service. Session operations authorize the authenticated principal or verified credential. Provider receipt handling follows provider verification and deduplicates across that provider. |
| Shared catalog | Billing `plans` and `plan_versions` | Billing serves approved catalog reads through its API. Catalog writes remain a restricted Billing operation. |

Within an owner, use composite tenant foreign keys for relationships between tenant rows. For example, the parent of an organizational unit is resolved by `(tenant_id, parent_id)` against `(tenant_id, id)`. A class group's academic year is resolved by `(tenant_id, school_id, year_id)` against `(tenant_id, school_id, id)`. Give each referenced key a matching unique constraint and index the referencing columns when needed. Make foreign owner references through the owning service or its approved projection, such as enrollment to a person and attendance to an enrollment. A tenant identifier on a row does not grant organizational or school-level permissions. The owner service checks those permissions on each operation.

Use the tenant-leading indexes and unique keys in the JSON. A payment attempt's idempotency key is unique within its tenant. A repeated request with the same payload returns its recorded outcome. Reuse with a different payload returns a conflict. A provider receipt is globally unique by provider and provider event ID. Billing verifies the callback, resolves the invoice and tenant using its own records, and commits the receipt and financial changes consistently. Preserve global uniqueness for verified domain hosts and inbox consumer/event pairs. Append-only revisions, ledger entries and audit records have no routine runtime update or delete grant.

## Roles and row policies

| Principal | PostgreSQL permissions |
| --- | --- |
| Owner API runtime | Owner-specific grants for permitted tables and statements according to the operating model. Tenant writes require the domain authorization check and the bound transaction context. |
| Owner worker runtime | Owner-specific grants following the operating model. The worker validates operation and tenant provenance through the owned service. |
| Schema owner | Separate non-login role that owns its schema and tables. |
| Migration runner | Separate login that can assume the reviewed schema owner role for approved migrations. |
| Gateway, public web, control panel | No database connection or table grants. |
| Support analyst | Authorized, masked API projection. No direct database connection. |

Use `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY` on every tenant and tenant-root table. Owner runtimes are non-owners with `NOSUPERUSER` and `NOBYPASSRLS`. They cannot inherit or assume a privileged role and have no `TRUNCATE` or schema `CREATE` grants. Revoke ambient access and scope explicit and default privileges to the owner's operations. The tenant policy uses `USING` for visible rows and `WITH CHECK` for newly inserted or updated rows. Both compare the tenant key with the bound UUID. An unset or empty value denies access. Keep policy predicates restrictive in combination and expose a domain-level error without foreign row details.

## Connection pooling

1. Authenticate and verify the tenant and authorization scope in the owner service. For an authenticated domain request, derive the active tenant from verified membership and scope. Public site reads resolve a verified host through the approved routing interface. Device ingestion resolves an authenticated device registration. A signed provider call uses the Billing-owned invoice or payment reference. Provider, device, host and tenant values are inputs to verification.
2. Validate the resolved tenant UUID before binding. Check out one physical connection, start a transaction and bind `app.tenant_id` with the transaction-local form of `set_config`. Use the same transaction and connection for all scoped statements. A caller that wants to switch tenant starts another transaction with independent authorization.
3. On success commit before returning the connection. On failure roll back before returning it. Discard a connection with an uncertain transaction state or failed cleanup. Transaction-local context expires at completion. Verify cleanup by reusing the same connection across both successful and failed tenant work.

Tenant context is only set by the trusted data layer using parameterized queries. Cross-tenant administration fans out into authorized, separately scoped transactions or uses an approved masked projection.

## API and event boundaries

The Gateway delegates final authorization and persistence to the owners. The operation map pins the tenant source for representative HTTP operations, including tenant provisioning, shared catalog reads, enrollment, attendance and provider callbacks. OpenAPI methods, paths and security requirements are governed by the Gateway compatibility check.

Keep the existing ten v1 event types and their producer, consumer and semantic deduplication keys. The producing owner binds the validated tenant for tenant effects. A global IAM revocation remains global at the IAM boundary. Any tenant-specific audit work derived from it requires an independently resolved, authorized tenant scope. A raw event payload never authorizes access.

Write the tenant outbox entry in the same transaction as the domain change through the Platform-owned append interface. Scope the interface to the bound tenant and registered event type. The dispatcher claim and delivery result are Platform-owned operations. The consumer validates the event and registers its inbox key before acting, atomically with the durable effect where both share the local database. External effects use a stable idempotency key or a new owned outbox entry. Acknowledge after the durable result. The unique consumer/event pair prevents accepting the same event under conflicting tenants.

## Acceptance for the database work

| Case | Required evidence |
| --- | --- |
| Tenant and owner boundaries | Tenant A cannot read, insert, update or delete tenant B's rows through a runtime role. An owner cannot directly read or write another owner's tables. The positive same-tenant case succeeds. |
| RLS and role definitions | Inspect deployed policies and role attributes. Exercise missing context, both policy clauses and same-owner tenant foreign keys with the runtime credential. |
| Pooled transactions | Reuse one physical connection from A to B after commit and rollback. Confirm an unbound request sees no tenant rows. A failed cleanup removes the connection from the pool. |
| Tenant and global unique keys | Check retry behavior within one tenant, legitimate reuse of a tenant-scoped key by a different tenant and intentional global uniqueness for provider receipts, verified hosts and event identity. |
| Durable events | Roll back the aggregate and outbox together. Confirm a replay does not repeat the durable effect. |

Run `node scripts/validate-postgres-tenant-contract.mjs` to check this design against the ownership, runtime, OpenAPI and event contracts. The validator is part of the repository policy check. The cases above exercise actual PostgreSQL in S02-W03-T02 and S02-W03-T03.
