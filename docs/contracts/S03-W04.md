# S03-W04 · MFA and recovery

| Field | Value |
| --- | --- |
| Version | 1.0.0 |
| Requirement | SEC-002 |
| Owner | IAM in Identity and Access |
| Foundations | [Gateway](S02-W02.md), [PostgreSQL](S02-W03.md), [IAM sessions](S03-W01.md) |

The Gateway reuses the current authenticated bearer session on these routes. Responses use the existing envelope and `Cache-Control: no-store`. An unavailable IAM dependency fails the request. Expired, consumed, mismatched and invalid proofs return generic validation errors. Attempt limits persist by actor and mode across runtimes.

| POST route | Operation | Request | 200 result |
| --- | --- | --- | --- |
| `/v1/auth/mfa/enroll` | `beginMfaEnrollment` | `password` | `challengeId`, `secret`, `otpauthUri`, `expiresAt` |
| `/v1/auth/mfa/enroll/confirm` | `confirmMfaEnrollment` | `challengeId`, `code` | Eight `recoveryCodes` shown once |
| `/v1/auth/mfa/step-up` | `verifyMfaStepUp` | `code` | `verifiedUntil`, at most five minutes from proof |
| `/v1/auth/mfa/recovery` | `requestMfaRecovery` | `password`, `recoveryCode` | `recoveryToken`, replacement `secret`, `otpauthUri`, `expiresAt` |
| `/v1/auth/mfa/recovery/confirm` | `confirmMfaRecovery` | `recoveryToken`, replacement authenticator `code` | Eight new `recoveryCodes`, `signInRequired: true` |

Enroll only after re-verifying the primary password. Verify possession by accepting a six-digit authenticator code once. The TOTP period is 30 seconds, with a one-step clock allowance and a strictly increasing counter per factor. Identity, current access session, session revision, tenant and membership all bind step-up to the current scope. The owner checks recent MFA as well as the current operation permission for sensitive mutations. Refresh, expiry, tenant switch, factor replacement and logout require new proof.

A user who loses their second factor signs in with their primary credential and submits an unused offline recovery code plus the primary password. The resulting ten-minute recovery capability is valid only for confirming the replacement on that exact session revision. It never authenticates a Gateway request or rotates a session. Recovery uses the replacement TOTP proof and atomically leaves the new factor active, replaces recovery codes and revokes the identity's existing sessions globally. Clients then sign in again. The old authenticator remains active until confirmation succeeds.

## Ownership, audit and controls

| Actor | Authority |
| --- | --- |
| Gateway | Authenticate, rate-limit and route. The IAM and domain owners make final decisions. |
| User with current session | Manage their own factor. A tenant-level step-up requires an active scoped membership. |
| Privileged user | A valid membership and applicable operation permission plus fresh MFA. The factor provides no new domain permissions. |
| IAM | Own the factor, pending action, code and session records and append credential-free audit facts. |
| Access and other owners | Obtain the scoped MFA decision through IAM and never query its factor tables. |

`0005-iam-mfa.sql` adds IAM-only global storage. Factor and pending-action seeds are encrypted with AES-256-GCM using an independent secret key and actor-bound authenticated data. The database stores only digests of recovery capabilities and backup codes. Recovery and enrollment challenges expire after ten minutes and allow no more than five verification attempts. The client treats seeds and backup codes as credentials and stores them offline as appropriate. Logs and events exclude seeds, codes, capability tokens, passwords and bearer tokens.

IAM appends `identity.mfa_enrolled.v1`, `identity.mfa_step_up.v1`, `identity.mfa_recovery_started.v1` and `identity.mfa_recovered.v1` facts in the same transaction as their corresponding effects. Each fact has an ID, identity ID, session ID, timestamp and the verified tenant and membership when scoped. Recovery also writes the existing `identity.session_revoked.v1` fact for each revoked session. The IAM facts are authoritative locally. Cross-context audit projection is addressed in S03-W05.

Run `node --test tests/S03-W04/*.test.mjs` against disposable loopback PostgreSQL 17. Before deploying, supply distinct, managed IAM signing, OTP and MFA keys and review the test and recovery procedure. For a migrated database, roll forward to a corrected migration or restore a tested backup according to the recovery plan.
