# S03-W02 · Users, persons and invitations

| Field | Value |
| --- | --- |
| Contract | `S03-W02` version `1.0.0` |
| Requirement | `FR-004`, `CORE-03` |
| Source of truth | [Ownership](S01-W03.json) · [Gateway v1](S02-W02.md) · [Tenant isolation](S02-W03.md) |

IAM keeps the global login identity. People keeps independent profiles in `people_fields.persons`; the same IAM identity can link to one profile in each tenant. Access keeps `identity_access.memberships` and the tenant-scoped `identity_access.invitations` introduced by migration `0003`. Each owner uses its own PostgreSQL role and transaction context.

## HTTP v1 and owner operations

| Operation | Input and result | Authorization |
| --- | --- | --- |
| `GET /v1/users` | Opaque Gateway cursor and `limit`. Rows include `id` and `displayName`. | Active tenant-wide membership and `people.user.read`. |
| `GET /v1/users/{userId}` | The path ID is the local person UUID. Missing or foreign IDs return `404`. | Active tenant-wide membership and `people.user.read`. |
| `POST /v1/users` | `{displayName, identityId?}` → `201`. The optional identity must be active and have an active membership in the tenant. Linked duplicates return `409`. | Active tenant-wide membership and `people.user.write`. |
| `POST /v1/memberships` | `{identityId, orgUnitId?}` → `201`. An existing active membership in the same scope is returned on retry. | Active membership, `access.membership.create` and owner-confirmed target unit when present. |
| `POST /v1/invitations` | `{identityId, orgUnitId?}` → `202` after trusted delivery handoff. Returns `invitationId`, `expiresAt` and `status` without the invitation secret. | Active membership, `access.invitation.create` and owner-confirmed target unit when present. |
| Owner `acceptInvitation` | Verified IAM principal, tenant UUID, invitation secret. Returns the selected tenant, membership and optional organization unit. | The invitation belongs to the principal, is still live, and can be consumed once. |
| Owner `selectContext` | Verified IAM principal and explicit tenant and membership UUIDs. | Confirms the membership belongs to the principal and the target tenant and is active and unexpired. |

Gateway route and operation IDs remain those of the existing OpenAPI catalog. Invitation acceptance and context resolution are internal owner operations. IAM issues sessions and validates context switches by calling the Access membership resolver. People and Access read authoritative scope from the verified session and current Access membership. Client-supplied tenant IDs never select the scope for list, get or create operations. Profile responses omit global identity keys and login/contact data. Profile routes remain tenant-wide until a profile-to-organization boundary is available. For delegation to an explicit branch, the creator must be scoped to that unit or hold eligible tenant-wide permissions, and the Tenancy owner must confirm the target unit belongs to the tenant.

## Invite and transaction lifecycle

1. Check that the target identity exists and is active through IAM. Authorize the creator through Access. Create a 32-byte random secret and write only its SHA-256 digest, target scope, creator membership and expiry. Tokens expire after 48 hours.
2. Hand off the secret to the trusted delivery port. A missing port prevents issuance. A failed handoff revokes an outstanding invitation and returns a generic `503`. The transport must keep the credential out of shared event payloads and logs. A failed revocation leaves the original bounded expiry in effect.
3. Verify the accepting IAM principal, bind the tenant transaction and lock the matching invitation. Check state and expiry, create or reuse the independent active membership, and mark the invitation consumed in the same committed transaction. Concurrency permits at most one acceptance per token. A token rejected in a different tenant or identity remains available to its intended recipient. Invitation acceptance grants membership in the requested scope. Role assignment requires the separate Access authorization path.
4. Resolve an explicit membership in the target tenant when switching context. A lookup with no membership ID succeeds only when exactly one eligible membership exists in the target tenant. Selected context contains only the new tenant and membership identifiers and optional unit. Permissions are resolved for each new context.

## Ownership and event permissions

| Principal | Allowed access |
| --- | --- |
| IAM runtime | Private global identities and sessions, validated membership lookup through the Access port. |
| People runtime | Tenant-local profile rows. When creating a profile, append `people.profile_changed.v1` through the Platform-owned function in the same transaction, with `person_id` and initial `version` only. |
| Access runtime | Own tenant-scoped memberships, invitations and their lifecycle, plus authorization through the Access policy. |
| Gateway | Authentication and routing, owner service authorization, and scoped cursors. |
| Tenant/branch actor | Membership, invitation and profile operations only within their verified permissions. |

The migration adds restrictive tenant policies to invitations, active-scope membership uniqueness and tenant-local linked profile uniqueness. Grants permit Access to update only invitation lifecycle fields. Check duplicate active memberships and linked profiles before applying the migration to an existing environment. Keep the migrations for prior tasks intact so their checksums remain verifiable.
