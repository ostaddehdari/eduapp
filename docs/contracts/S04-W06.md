# S04-W06 · Platform and organization management

| Contract | Version | Requirement |
| --- | --- | --- |
| S04-W06 | 1.0.0 | Platform owner and organization manager views |

The Persian control panel exposes authorized customer summaries, organizational branches, plan quotas, manager roles and the two-person review of tenant status changes. Login and bearer scope use the existing IAM contract. Customer UUIDs select records within authority resolved by the Gateway. They do not create authority.

## Ownership and read scope

| Viewer | Visible information |
| --- | --- |
| Allowlisted platform operator with a global session | Authorized customer summaries and selected-tenant details. |
| Organization manager with an active tenant-wide grant | Its own tenant summary, eligible branches, quotas and manager roles. |
| Branch-scoped manager | Its tenant summary, exact authorized branch and that branch's manager roles. Global quotas and approvals are outside that scope. |
| Unauthorized or anonymous caller | No management records. |

Tenancy owns tenant lifecycle and review records. Access owns membership and manager roles. Billing owns entitlement quota values. The panel consumes the management owner's bounded, permission-checked projections. Manager summaries use role and organization scope and do not display contact or authentication data. The UI holds its access token in memory, clears it on sign-out and refuses organization responses carrying another tenant ID.

## Gateway interface

| Method and path | Payload or response |
| --- | --- |
| `GET /v1/management/overview` | Organization scope derives from the verified session. A platform caller can use optional `tenantId` to select an allowlisted customer. |
| `POST /v1/management/status-requests` | `{tenantId,targetStatus,expectedVersion}`. Creates pending approval for suspension or reactivation. Returns 201. |
| `POST /v1/management/status-requests/{requestId}/decision` | `{tenantId,decision}` where decision is `approve` or `reject`. Returns the recorded result. |

The read envelope contains `{mode,tenants,selected}`. Customer summaries include ID, slug, display name, status and version. A selected record includes the tenant summary, branches, quotas, managers, approvals, and permission flags for requesting and deciding status changes. An approval includes ID, target status, state, expected tenant version, request and decision timestamps, and a per-viewer `canDecide` flag. Quota limits are decimal strings or null to preserve precision. Sample dates and browser displays use Persian locale conventions where applicable.

The initial platform overview lists bounded authorized tenant summaries. Details are returned only for a selected authorized tenant. Organization scope returns its single allowed tenant. Review states are `pending`, `approved`, `rejected` and `stale`. A pending request preserves the tenant's status. An approved request updates only the matching version. A stale result requires a new request.

## Approval rules

Only authorized platform operators can create or decide status requests. The requester cannot decide their own request. Both writes require fresh second-factor verification on the same session. The browser calls `POST /v1/auth/mfa/step-up` before attempting the command. It sends the code only to IAM. The backend independently verifies actor, scope, role, freshness and version and records the review lifecycle. The browser only offers an action when the matching permission and approval state allow it. Refreshing reads the current customer and approval status from the server.

## Preview and verification

Open `?view=management` from the panel. `VITE_EDUAPP_API_BASE=/eduapp/api` enables the same-origin Gateway at build time. The build without that variable shows two explicitly fictional organizations with separate scope views. A platform preview can switch between the sample requester and reviewer to rehearse the approval. That mode performs no live API requests or customer updates and does not collect login or verification credentials.

```sh
corepack pnpm --filter @eduapp/control-panel typecheck
node --test tests/S04-W06/browser.test.mjs
```

The Chromium tests build at a relative asset base and exercise the embedded panel using a local HTTP fixture. They verify RTL and mobile fit, distinct sample scopes, no network actions from the demo, step-up failure and retry, separate requester and reviewer, tenant isolation and the lack of persisted credentials. The native Gateway/database tests remain independent of the browser fixture.
