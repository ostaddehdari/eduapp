# S02-W05 · Observability and environment secrets

| Contract | Version | Requirement | Status |
| --- | --- | --- | --- |
| S02-W05 | 1.0.0 | OPS-002 | Dev/staging Gateway baseline |

The [proposal](../../proposal.md) specifies request correlation, operational signals and environment separation. The [Gateway contract](S02-W02.json) owns public health paths and the existing request-ID response behavior. The [service operating model](../architecture/service-boundary-operating-model.v1.json) requires isolated databases and credentials per environment.

## API and events

| Interface | Owner and behavior |
| --- | --- |
| `GET /v1/health/live` | Gateway. Checks that the process can serve requests. API unavailability does not change liveness. |
| `GET /v1/health/ready` | Gateway. Checks the configured local API's `GET /api/health`. In staging this dependency is mandatory. Unavailable or timed-out dependencies return the existing generic 503 and generated request ID. Dev can run Gateway alone. |
| `GET /metrics` | Platform. Prometheus text on the dedicated loopback listener. It is outside the public Gateway and SDK contracts. |
| `gateway.request.completed` (v1) | Gateway. Request ID, trace and span IDs, registered operation ID, fixed method category, status and duration. Interruption uses status 0. |
| `gateway.readiness.checked` (v1) | Gateway. Correlation IDs, parent span, elapsed time and boolean readiness. The loopback API probe receives the generated request ID and W3C traceparent. |
| `gateway.alert` (v1) | Platform. GatewayReadiness fires on transition into dependency failure and resolves on recovery. Repeated failures keep the gauge at zero without repeating the same transition. |

Telemetry records share a version, event, timestamp, runtime name and environment. Their trace IDs are generated at the Gateway so external headers cannot forge the recorded correlation. The only metrics dimensions are registered operation, method, status and histogram bucket. Requests without a registered operation use a constant label. Readiness has no sample until the first completed probe.

## Ownership, permissions and secrets

| Principal | Access |
| --- | --- |
| Gateway process | Emits the fixed event schemas and probes the configured loopback API port. Controls its process-local counters and gauges. |
| Local monitoring process | Reads the metrics listener and collects allowlisted log fields in its own environment. |
| Operators | Read telemetry for their authorized environment. A separate deployment identity configures the credentials of each service. |
| Tenant users and public clients | Use the versioned Gateway API and receive its existing request ID. They have no route to scrape internal metrics. |

There is no application table, schema migration or domain broker topic for baseline telemetry. Platform owns any future collection and lifecycle configuration. Runtime metrics reset on restart. Log forwarding, retention and destination access are configured by each environment's operator.

Only defined fields reach the telemetry sink. Headers and cookies, raw URL, path parameters, query and body, person and tenant IDs, credentials, IPs, database details, exception text and stack traces are omitted. Sink failures raise a dropped-record counter without blocking Gateway replies. A health response contains only the existing status envelope.

Provision development, staging and production credentials separately in the deployment secret store with a service-specific identity. Keep per-environment credentials and database contents isolated. Use synthetic data for local and staging checks. Keep secrets out of the repo, startup arguments, telemetry events and metric labels. The implemented loopback checks use no credentials and accept no secret values from config. Billing and queue-specific signals require integration by their owner services, which can use the same field minimization rules.
