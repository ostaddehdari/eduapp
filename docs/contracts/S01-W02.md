# قرارداد سفر تجاری، مالکیت داده و ایجاد نخستین مدرسه

- شناسه: `S01-W02`
- نسخه: `1.0.0`
- وضعیت: پذیرفته‌شده
- تاریخ تصویب: ۱۴۰۵/۰۹/۰۲ (`2026-11-23`)
- الزامات: `FR-003` و وابستگی تجاری `FR-006`
- قرارداد ماشین‌خوان: [`S01-W02.json`](S01-W02.json)

## ۱. هدف و مرز

این قرارداد مسیر بازدیدکننده از مشاهده پلن تا خرید تأییدشده، ساخت Tenant، ایجاد سازمان و ایجاد نخستین مدرسه مستقل یا شعبه‌ای را مشخص می‌کند. این سند قرارداد اجرایی است، نه ادعای پیاده‌سازی Backend. داده واقعی، کلید درگاه و اطلاعات مشتری در مخزن قرار نمی‌گیرد.

اصل قطعی: callback پرداخت به‌تنهایی اشتراک یا Tenant را فعال نمی‌کند. Billing ابتدا امضا یا استعلام Provider را تأیید، رویداد را deduplicate، ledger و entitlement را در تراکنش مالک ثبت و سپس رویداد نسخه‌دار منتشر می‌کند.

## ۲. جریان و وضعیت‌ها

| مرحله | Actor | عملیات | وضعیت خروجی |
|---:|---|---|---|
| ۱ | بازدیدکننده | `GET /plans` | `PLAN_SELECTED` |
| ۲ | خریدار احرازشده | `POST /subscriptions/checkout` | `CHECKOUT_CREATED` |
| ۳ | خریدار/پرداخت‌کننده | `POST /invoices/{invoiceId}/payment-attempts` | `PAYMENT_PENDING` |
| ۴ | Provider تأییدشده | `POST /webhooks/payments/{provider}` | `PAYMENT_VERIFIED` |
| ۵ | Provisioning Service | `POST /tenants` پس از رویداد تأییدشده | `TENANT_ACTIVE` |
| ۶ | مالک Tenant | `POST /org-units` | `FIRST_ORG_CREATED` |
| ۷ | مالک Tenant | `POST /schools` | `FIRST_SCHOOL_CREATED` |
| ۸ | مالک Tenant | `GET /me/capabilities` و تکمیل checklist | `ONBOARDING_COMPLETE` |

تمام mutationهای تکرارپذیر `Idempotency-Key` یا کلید منطقی پایدار دارند. کلید با actor، operation و hash بدنه canonical مقایسه می‌شود؛ استفاده همان کلید با payload متفاوت `409` است.

## ۳. قرارداد API و خطا

| Operation | مالک | Actor و مجوز | موفق | خطاهای اصلی |
|---|---|---|---:|---|
| `listPlans` | Billing | عمومی، فقط خواندن نسخه فعال پلن | ۲۰۰ | ۴۲۹ |
| `createCheckout` | Billing | نشست فعال و payer معتبر | ۲۰۱ | `401`, `409`, `422`, `429` |
| `createPaymentAttempt` | Billing | payer همان invoice | ۲۰۲ | `403`, `404`, `409`, `422` |
| `receivePaymentWebhook` | Billing | امضا/استعلام Provider و dedupe | ۲۰۰ | `401`, `409`, `422` |
| `createTenant` | Tenancy | فقط Provisioning با payment verified یا Platform Admin | ۲۰۱ | `403`, `409`, `422` |
| `createOrgUnit` | Tenancy | Tenant Owner در scope فعال | ۲۰۱ | `403`, `404`, `409`, `422` |
| `createSchool` | School | Tenant Owner؛ org unit همان Tenant | ۲۰۱ | `403`, `404`, `409`, `422` |

خطاها envelope استاندارد `error.code`, `error.message`, `details[]` و `meta.requestId` دارند. برای شناسه متعلق به Tenant دیگر از `404` و کد غیرقابل افشا استفاده می‌شود.

## ۴. قرارداد رویداد

Envelope مشترک: `eventId`, `eventType`, `schemaVersion`, `tenantId`, `aggregateId`, `occurredAt`, `traceId`, `payload`. مصرف‌کننده پیش از اثر جانبی `inbox_dedup` را ثبت می‌کند.

| رویداد | Producer | Consumer اصلی | کلید تکرار |
|---|---|---|---|
| `billing.payment_verified.v1` | Billing | Billing | provider + providerEventId |
| `billing.subscription_activated.v1` | Billing | Provisioning | subscriptionId + activationRevision |
| `tenancy.tenant_created.v1` | Tenancy | Access | tenantId |
| `tenancy.org_unit_created.v1` | Tenancy | School | orgUnitId |
| `school.school_created.v1` | School | Onboarding | schoolId |
| `onboarding.completed.v1` | Onboarding | Analytics | tenantId + journeyVersion |

Payload رویداد حداقلی و بدون شماره کارت، OTP، داده کودک یا secret است. Consumer از `tenantId` پیام بیرونی برای مجوز اعتماد نمی‌کند.

## ۵. مالکیت جدول و تراکنش

| مالک دامنه | جداول تحت مالکیت | قاعده نوشتن |
|---|---|---|
| IAM | `identities`, `sessions` | فقط IAM؛ هویت ورود سراسری، نشست scopeدار |
| Billing | `plans`, `plan_versions`, `subscriptions`, `invoices`, `payment_attempts`, `provider_events`, `ledger_entries`, `entitlements` | تراکنش پرداخت، ledger و outbox در مرز Billing |
| Tenancy | `tenants`, `org_units` | FK مرکب Tenant؛ parent هم‌Tenant؛ درخت بدون چرخه |
| Access | `memberships`, `roles`, `role_bindings` | عضویت و scope؛ نقش Tenant قبلی حمل نمی‌شود |
| School | `schools` | org unit مدرسه باید متعلق به همان Tenant باشد |
| Platform | `outbox_events`, `inbox_dedup`, `audit_events` | append-only و payload حداقلی |

هیچ سرویس دیگری جدول مالک را مستقیم تغییر نمی‌دهد. Billing فقط event فعال‌سازی منتشر می‌کند؛ Provisioning/Tenancy Tenant را ایجاد می‌کند. تغییر org parent با version check و کنترل چرخه انجام می‌شود.

## ۶. ماتریس مجوز

| Actor | مجاز | ممنوع |
|---|---|---|
| Visitor | مشاهده پلن | Checkout، Tenant، Org، School |
| Authenticated Buyer | Checkout و Payment Attempt فاکتور خودش | Webhook، Tenant، Org، School |
| Payment Provider | Webhook تأییدشده | ساخت Tenant/Org/School |
| Provisioning Service | ساخت Tenant پس از payment verified | پرداخت، Org و School |
| Platform Admin | ساخت دستی Tenant با Audit | جعل Webhook |
| Tenant Owner | ساخت Org/School و مشاهده capabilities | Webhook و ساخت Tenant جدید خارج فرآیند |
| School Admin | capabilities و عملیات مدرسه در scope مراحل بعد | Tenant، Org root و Webhook |

مجوز با membership فعال، scope، نقش و entitlement تعیین می‌شود؛ شناسه در request به‌تنهایی مجوز نیست.

## ۷. مدل مدرسه مستقل و شعبه‌ای

- مدرسه مستقل: org unit نوع `school` در ریشه Tenant و رکورد `schools` متصل به همان org unit.
- مجموعه شعبه‌ای: org unit والد مجموعه، child نوع `branch` و child مدرسه یا school متصل به branch طبق policy نسخه‌دار.
- parent خارج Tenant با `ORG_PARENT_NOT_FOUND`، چرخه با `ORG_CYCLE` و کد تکراری در یک parent با `ORG_CODE_CONFLICT` رد می‌شود.
- root code در Tenant و sibling code در parent باید unique باشند.

## ۸. سناریوهای پذیرش و منفی

1. خرید تأییدشده → Tenant → مدرسه مستقل: پذیرفته شود.
2. خرید تأییدشده → Tenant → مجموعه/شعبه → مدرسه: پذیرفته شود.
3. تکرار یک provider event: فقط یک ledger، entitlement و Tenant ایجاد شود.
4. callback تأییدنشده: `PAYMENT_NOT_VERIFIED` و هیچ Tenant ساخته نشود.
5. parent از Tenant دیگر: `ORG_PARENT_NOT_FOUND` بدون افشای منبع.
6. ایجاد چرخه: `ORG_CYCLE`.
7. code تکراری زیر یک parent: `ORG_CODE_CONFLICT`.
8. اتصال School به org unit Tenant دیگر: `ORG_UNIT_NOT_FOUND`.

## ۹. نسخه‌بندی و تغییر

Breaking change در operation، event یا مالکیت جدول نیازمند افزایش major، ADR اثر داده و PR بازبینی‌شده است. افزودن فیلد optional با minor و اصلاح توضیح با patch انجام می‌شود. Rollback این نسخه، پیش از پیاده‌سازی داده، فقط revert سند و validator است؛ پس از ورود migration باید migration جبرانی و snapshot آزموده‌شده داشته باشد.
