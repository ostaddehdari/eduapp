## API

| Operation | Request | Authorized result |
| --- | --- | --- |
| `createTenant` | `POST /v1/tenants`, verified caller, `Idempotency-Key`, JSON creation fields | `201` with active Tenant, legal entity and first owner membership |
| `getTenant` | `GET /v1/tenants/{tenantId}`, selected membership | `200` for an active Tenant in the selected authorized scope |
| `listTenants` | `GET /v1/tenants`, Gateway pagination | `200` with the authorized active selected Tenant or an empty page |
| `updateTenantStatus` | `PATCH /v1/tenants/{tenantId}/status`, platform administrator, JSON `status` and `expectedVersion` | `200` with the active or suspended Tenant |

Creation accepts a lowercase slug of 3–63 letters, digits and interior hyphens, a display name of 1–160 characters, and an active IAM `ownerIdentityId`. `legalEntity` requires a name of 1–160 characters, a two-letter uppercase `countryCode`, and a registration number of 1–64 characters. Optional `trialDays` is an integer from 1 to 30. It records a UTC trial cutoff while access and entitlements remain subject to later Billing policy. It never changes the Tenant status automatically.

An item includes `id`, `slug`, `displayName`, `status`, `ownerIdentityId`, `ownerMembershipId`, `legalEntity`, nullable `trialEndsAt`, `version`, `createdAt` and `updatedAt`. Item responses include the version ETag. A repeated status at the current version returns the current representation. A stale version returns `412`. A request for another Tenant uses a generic `404`. Exact create replay returns the stored original response. A conflicting payload, duplicate slug or repeated redemption of the same verified payment returns `409`.

## Authority and data

| Principal | Permission |
| --- | --- |
| Anonymous caller or ordinary buyer | Public commerce only, with no Tenant creation authority |
| Provisioning service | Create when its owner callback verifies a committed Billing proof |
| Platform administrator | Manual creation and activation or suspension after trusted platform authorization |
| Tenant owner | Read the selected active Tenant and manage its organization through scoped owner permissions |
| Access | Bootstrap the first owner membership and built-in role only for a pending verified registry handoff |
| Platform outbox | Store the minimal Tenant creation event |

Billing proof and platform clearance come from trusted server authorization callbacks. A caller cannot assert either using a body or header. A verified payment reference remains stable across retries and is persisted only as a digest. The source-owned create command binds the Gateway namespace and normalized payload to a durable result. The command, Tenant, legal entity, first owner, outbox event and audit fact commit together.

Tenancy owns `tenants`, `legal_entities`, `registry_create_commands` and `registry_audit_facts`. Access owns `registry_owner_receipts`, `memberships`, `roles` and `role_bindings`. The narrowly granted Access function checks the bound new Tenant receipt, confirms that the requested identity is active, and creates the first membership and built-in role. The runtime has no direct grants to foreign tables. Forced RLS remains active on all scoped tables. Registry audit is append-only and records action, actor, request ID, Tenant and UTC time. It omits legal entity identifiers and payment data.

The `tenancy.tenant_created.v1` Platform event targets Access with the Tenant ID as its semantic key and only `tenantId` in the payload. Access provisioning itself has already committed when the event leaves the outbox. Active status is required for normal Tenant operations. Suspension preserves records and prevents use through active-scope checks pending a newly authorized reactivation.
