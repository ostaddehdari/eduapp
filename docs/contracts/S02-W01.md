# قرارداد Monorepo، مالکیت و CI

- شناسه: `S02-W01`
- نسخه: `1.0.0`
- وضعیت: پذیرفته‌شده
- الزام: `OPS-001`
- قرارداد ماشین‌خوان: [`S02-W01.json`](S02-W01.json)

## ۱. محدوده این Task

این Task فقط قرارداد نسخه‌دار ساختار مخزن، مالکیت، CI، API/رویداد/جدول و ماتریس مجوز را تثبیت می‌کند. ساخت واقعی workspace، برنامه‌های NestJS/Nuxt/React، Workflowهای PR، `CODEOWNERS` و Rule محافظت `main` در `S02-W01-T02` انجام می‌شود. این قرارداد هیچ مجوزی برای production، تغییر Nginx، migration یا داده واقعی صادر نمی‌کند.

## ۲. ساختار Monorepo

مدیر workspace هدف `pnpm` با lockfile اجباری است. چهار واحد runtime باید مسیر و مالک یکتا داشته باشند:

| واحد | فناوری | مسیر | مالک منطقی | فرمان‌های اجباری PR |
|---|---|---|---|---|
| API | NestJS | `apps/api` | backend | lint، typecheck، test، build |
| Worker | NestJS | `apps/worker` | backend | lint، typecheck، test، build |
| وب عمومی | Nuxt | `apps/public-web` | public_web | lint، typecheck، test، build |
| پنل کنترل | React | `apps/control-panel` | control_panel | lint، typecheck، test، build |

قراردادهای مشترک در `packages/contracts`، تنظیمات مشترک در `packages/config` و ابزار تست در `packages/test-utils` قرار می‌گیرند. هیچ package مشترکی اجازه import از `apps/*` ندارد. frontendها نیز مجاز به import داخلی backend یا دسترسی مستقیم دیتابیس دامنه نیستند.

## ۳. مالکیت مسیر و داده مخزن

مالک bootstrap فعلی GitHub، `@ostaddehdari` است؛ در عین حال مسئولیت منطقی مسیرها میان platform، backend، public_web، control_panel، contracts، security و ci جدا ثبت می‌شود. در Task بعدی تمام مسیرهای حساس و یک fallback سراسری در `CODEOWNERS` نوشته می‌شوند.

داده این قرارداد «داده مخزن» است، نه جدول محصول: workspace manifest و lockfile متعلق به platform، workflowها متعلق به ci، `CODEOWNERS` متعلق به security و قراردادهای API/رویداد متعلق به contracts هستند. هر artifact دقیقاً یک مالک دارد.

## ۴. قرارداد API، رویداد و جدول

این Task هیچ endpoint، رویداد دامنه یا جدول دیتابیس جدیدی اضافه نمی‌کند. مالکیت API، رویداد و جدول تعریف‌شده در `S01-W03` تا انتقال کنترل‌شده معتبر می‌ماند.

- OpenAPI و schemaهای رویداد باید نسخه‌دار و زیر مالکیت `packages/contracts` باشند.
- GitHub webhook و نتیجه CI رویداد دامنه محصول محسوب نمی‌شوند.
- CI و jobهای Pull Request هیچ credential دیتابیس production دریافت نمی‌کنند و اجازه نوشتن جدول دامنه را ندارند.
- تغییر breaking در API، event envelope یا مالک جدول به نسخه major، ADR و برنامه migration/reconciliation نیاز دارد.

## ۵. قرارداد CI و محافظت main

هر Pull Request به `main` باید چک repository-policy، چهار چک runtime و dependency-boundaries را بگذراند. هر runtime چهار فرمان lint، typecheck، test و build دارد. permission پیش‌فرض Workflow فقط `contents: read` و `pull-requests: read` است و `id-token` غیرفعال می‌ماند.

هدف محافظت `main`:

- تغییر فقط از Pull Request و با required checkهای strict؛
- حل‌شدن conversationها پیش از Merge؛
- ممنوعیت force push و حذف branch؛
- عدم اجرای کد PR غیرقابل‌اعتماد روی Runner production؛
- deployment فقط از Workflow جدا، commit روی main و تأیید مستقل.

مخزن فعلاً یک مالک تأییدشده دارد؛ بنابراین bootstrap با صفر approval ولی required checkهای کامل آغاز می‌شود تا author در قفل خودتأییدی نماند. به‌محض اضافه‌شدن reviewer یا team دوم، حداقل یک approval و code-owner review اجباری می‌شود. این استثناء باید در Task عملیاتی شواهد داشته باشد و bypass خاموش و پنهان مجاز نیست.

## ۶. ماتریس مجوز

| Actor | مجاز | ممنوع |
|---|---|---|
| نویسنده PR | پیشنهاد تغییر و دیدن نتیجه چک | دورزدن چک، secret production و deploy |
| Code owner | بازبینی مسیر مالک و درخواست اصلاح | خاموش‌کردن چک امنیتی و بازبینی مستقل تغییر خود |
| Repository admin | مدیریت rule بازبینی‌شده و bypass اضطراری مستند | bypass پنهان و force push به main |
| Runner میزبانی‌شده PR | خواندن سورس، اجرای چک و نتیجه پاک‌سازی‌شده | secret، دیتابیس و deployment production |
| Runner production | deployment allowlisted و جداگانه تأییدشده | اجرای کد PR و shell دلخواه root |
| Backend runtime | repository دامنه مالک و قرارداد نسخه‌دار | نوشتن جدول بیگانه و import frontend |
| Frontend runtime | HTTP نسخه‌دار و قرارداد presentation | دیتابیس دامنه و import داخلی backend |

## ۷. سناریوهای پذیرش

1. چهار runtime مسیر، فناوری، مالک و چهار فرمان اجباری یکتا داشته باشند.
2. تمام مسیرهای runtime و حساس rule صریح `CODEOWNERS` داشته باشند.
3. مسیر تکراری با `DUPLICATE_WORKSPACE_PATH` رد شود.
4. import داخلی backend از frontend با `FORBIDDEN_DEPENDENCY` رد شود.
5. حذف required check با `REQUIRED_CHECK_MISSING` رد شود.
6. دریافت secret از PR با `PR_SECRET_ACCESS_DENIED` رد شود.
7. دسترسی CI به دیتابیس production با `CI_PRODUCTION_ACCESS_DENIED` رد شود.
8. deployment از PR با `DEPLOYMENT_APPROVAL_REQUIRED` رد شود.

## ۸. نسخه‌بندی و Rollback

تغییر مسیر runtime، مالک logical، نام required check یا مرز dependency breaking است و نسخه قرارداد را تغییر می‌دهد. چون این Task فقط سند و validator است، rollback با Git revert بازبینی‌شده انجام می‌شود و هیچ اقدام سرور یا دیتابیس لازم نیست.
