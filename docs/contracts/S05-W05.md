# S05-W05 · درگاه و استعلام پرداخت

نسخه `1.0.0`؛ `FR-006`؛ مالک تمام تغییرات مالی `commercial_billing`. این قرارداد برای adapter یک درگاه مشخص است؛ هیچ توکن، مرجع یا نتیجهٔ بازگشت مرورگر به تنهایی پرداخت موفق نیست.

| عملیات | کنترل و نتیجه |
| --- | --- |
| `begin(identity, orderId, requestKey)` | فقط عضو مجاز همان tenant؛ سفارش pending/grace، قیمت ثبت‌شده و کلید UUID؛ adapter درگاه با همان کلید idempotency مرجع را صادر می‌کند؛ تلاش پرداخت pending و مرجع یکتا ثبت می‌شود. |
| `callback(rawBody, signature, timestamp)` | HMAC-SHA256 روی `timestamp.rawBody`، پنجرهٔ ۵ دقیقه، بدنهٔ حداکثر ۸ KiB؛ استعلام مستقل سروری با reference؛ تطبیق provider، tenant، attempt، invoice، مبلغ و ارز. |
| نتیجهٔ موفق | در یک تراکنش: event یکتا، attempt verified، order/invoice paid، subscription active، یک credit ledger و entitlement برای هر ماژول خریداری‌شده. پنج callback برای همان attempt فقط یک بار اثر مالی دارند. |

داده و دسترسی: migration `0016-payment-verification.sql` به `payment_attempts` مرجع یکتای درگاه می‌افزاید، `verified_callbacks` با کلید `(provider,event_id)` و RLS اجباری می‌سازد، و credit هر invoice و feature هر subscription را یکتا می‌کند. runtime فقط با `eduapp_billing_api` و tenant transaction کار می‌کند. payload رویداد برای audit هش می‌شود؛ کلید webhook در مخزن ذخیره نمی‌شود. پاسخ callback تکراری `replayed` است، اما payload متفاوت برای شناسهٔ رویداد قبلی رد می‌شود. اختلاف مبلغ، لغو سفارش یا تلاش متعلق به tenant دیگر پرداخت را فعال نمی‌کند.

مسیر HTTP اختیاری `POST /v1/webhooks/payments/{provider}` با پیکربندی `commerce.payment` در runtime فعال می‌شود؛ بدنهٔ خام و دو هدر `x-payment-signature` و `x-payment-timestamp` به verifier سپرده می‌شود. credential و adapter واقعی تنها پس از انتخاب provider و آماده شدن backend تولید وارد می‌شوند. `provider.createIntent` باید با `requestKey` در خود provider هم idempotent باشد تا rollback دیتابیس مرجع تازه نسازد. پیش از migration تولید backup، مالک دیتابیس، بررسی checksum و طرح rollback لازم است.
