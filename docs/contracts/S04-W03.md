# S04-W03 · Organization and school setup

| Contract | Version | Requirement |
| --- | --- | --- |
| S04-W03 | 1.0.0 | FR-003 · Organization and school onboarding |

EduApp uses a Persian, right-to-left wizard to set up the first organization, school, manager invitation and site draft. An authorized tenant-wide owner proceeds through four ordered steps. The API owns the transition and saved version so a second tab or an interrupted session can resume safely.

## Wizard steps

| Step | Input | Result |
| --- | --- | --- |
| `organization` | `kind`, `name`, `code` | Initial organization in the selected tenant. Kinds are holding, company, collection, school and institute. |
| `school` | `layout`, `name`, `code`, and branch name and code when `layout=branch` | Standalone school, or the first school under a branch of a company or collection. |
| `invitation` | `identityId` | Manager invitation is created through the owned invitation service after recent second-factor verification. The UI distinguishes a queued invitation from an already recorded item. |
| `site` | `name`, `slug` | First site draft. Publication is a separate owner operation. |

The terminal `completed` step summarizes the completed work. User-facing statuses come from the response. Display names and slugs remain tenant-scoped. Page state includes no password, second-factor code, invitation token or access credential.

## HTTP scope and resume

| Operation | Request and result |
| --- | --- |
| `GET /v1/onboarding` | Use the current bearer session. Return `{version, step, draft}` for its selected tenant in the data envelope. A new tenant starts at the organization step. |
| `POST /v1/onboarding/advance` | Use the same bearer session and post `{expectedVersion, step, input}`. Return the next current state. Step and version must match the server. |
| `POST /v1/auth/mfa/step-up` | Verify a one-time code on the current session before sending the invitation advance. The code is not part of the wizard request. |

The UI does not send a tenant ID or role in wizard requests. The authenticated Gateway applies the tenant scope and delegates to the appropriate owner. A submitted login may select a tenant, and the API verifies membership. The UI checks the returned tenant before loading the wizard. It keeps the access token only in memory and reloads stored progress after the next sign-in. A response from an earlier session cannot replace the current account's progress. The resume screen offers a new server read after a conflicting advance.

Tenancy owns organization data and wizard progress. School-shaped org units follow the [Organization Tree contract](S04-W02.md). Access owns manager invitations, IAM owns second-factor checks, and Sites owns the first site draft. The browser requires permission from the authenticated API and has no direct table access. Tenant records, invitations and site drafts use their corresponding owner operations. This flow adds no public release or publishing action.

## Local use and sample mode

From the control panel open `?view=onboarding`. A build with `VITE_EDUAPP_API_BASE=/eduapp/api` uses the same-origin Gateway and appends `/v1` to that path. It requires a tenant-enabled account, a selected tenant membership and access to its second factor. Set the variable at build time when the Gateway routes are available behind that path.

With no API base at build time, the wizard is an explicitly labeled practice flow for the two sample schools. It uses per-school browser storage for sample progress and offers a reset. It does not contact the live API, collect a manager identity or credential, issue an invitation, or create and publish a real site. Use fictional names and codes in the practice form.

Run the [acceptance suite](../../tests/S04-W03/README.md) for both modes.
