# قرارداد مرز سرویس، مالکیت داده و معماری استقرار

- شناسه: `S01-W03`
- نسخه: `1.0.0`
- وضعیت: پذیرفته‌شده
- الزام: `DATA-001`
- قرارداد ماشین‌خوان: [`S01-W03.json`](S01-W03.json)

## ۱. تصمیم معماری

شروع محصول یک API ماژولار NestJS و worker با مرزهای دامنه‌ای صریح است؛ وب عمومی Nuxt و پنل React فقط HTTP نسخه‌دار مصرف می‌کنند. «ماژول منطقی» به معنی سرویس مستقل، دیتابیس مستقل یا container جدا از روز اول نیست. split فقط با داده بار/تیم/SLO، آمادگی قرارداد و migration و ADR هزینه‌دار مجاز می‌شود.

شکل اولیه شامل `api`، `worker`، `public-web` و `control-panel` و PostgreSQL مشترک فیزیکی است. Redis و RabbitMQ تا سنجه یا POC الزام نیستند؛ Redis هرگز source of truth و broker هرگز جایگزین transactional outbox نیست.

هر context فقط repository و مدل ORM خودش را دارد. اشتراک کد به قرارداد، value object و ابزار عمومی محدود است؛ repository مشترک بین مالک‌ها ممنوع است.

## ۳. مالکیت جدول

۳۶ جدول proposal به ۱۲ مالک دامنه‌ای و دقیقاً یک context نگاشت شده‌اند. نوشتن مستقیم جدول context دیگر با `FOREIGN_DATA_OWNER` رد می‌شود. ارتباط بین contextها فقط application service داخلی با مرز صریح، API نسخه‌دار یا رویداد نسخه‌دار است.

قواعد `DATA-001`:

- ردیف Tenant-owned دارای `tenant_id NOT NULL` است.
- FK مشترک از `(tenant_id, foreign_id)` استفاده می‌کند.
- RLS دفاع تکمیلی است و authorization برنامه را حذف نمی‌کند.
- pool reuse باید context قبلی را reset و context جدید را bind کند.
- تراکنش مالی idempotent و ledger append-only است.
- aggregate و outbox در یک تراکنش نوشته می‌شوند؛ consumer پیش از side effect، inbox dedupe را ثبت می‌کند.

## ۴. مالکیت API و رویداد

هر ۱۴ tag فعلی OpenAPI یک context مالک دارد و در validator تمام operationIdها دقیقاً یک‌بار شمارش می‌شوند. Gateway فقط authentication اولیه، rate limit و route را انجام می‌دهد؛ authorization نهایی همیشه نزد context مالک است.

ده رویداد نسخه‌دار، producer، consumer و dedupe key دارند. payload رویداد برای مجوز کاربر کافی نیست و نباید secret، داده کارت یا PII غیرضروری حمل کند.

## ۵. ماتریس دسترسی معماری

| Actor فنی | مجاز | ممنوع |
|---|---|---|
| API Gateway | auth اولیه، rate limit، route | DB write و authorization نهایی دامنه |
| Context Module | جدول مالک، command مالک، event نسخه‌دار | جدول بیگانه و اعتماد به tenantId بیرونی |
| Worker Consumer | dedupe و application service مالک | SQL بین contextها و مجوز از payload |
| Public Web | HTTP عمومی نسخه‌دار | DB و event داخلی |
| Control Panel | HTTP احرازشده نسخه‌دار | DB و دورزدن business rule |
| Migration Runner | migration بازبینی‌شده schema مالک | runtime و migration بیگانه |
| Support Analyst | read model مجاز و mask‌شده | PII خام و write مستقیم production |

## ۶. دروازه split

جداسازی runtime خودکار نیست. `contract_readiness`، `data_migration_readiness` و `cost_review` همیشه لازم‌اند و حداقل یکی از مالکیت تیم مستقل، فشار اندازه‌گیری‌شده ۳۰روزه یا SLO/امنیت مستقل نیز باید وجود داشته باشد. خروجی فقط «مجاز برای ADR بازبینی‌شده» است، نه split فوری.

ADR باید تیم و on-call، API/event compatibility، SLO، trace/metric/log، شبکه و secret، migration و reconciliation، rollback و restore drill و هزینه CI/CD را ثبت کند.

## ۷. سناریوهای پذیرش

1. تمام operationهای OpenAPI مالک context داشته باشند.
2. هر ۳۶ جدول proposal فقط یک مالک داشته باشد.
3. نوشتن مستقیم جدول بیگانه با `FOREIGN_DATA_OWNER` رد شود.
4. reuse اتصال بین Tenant A/B بدون نشت و با `TENANT_CONTEXT_MISMATCH` fail-closed باشد.
5. replay فرمان مالی تنها یک اثر ledger داشته باشد.
6. replay رویداد پیش از side effect حذف شود.
7. split بدون evidence با `SPLIT_EVIDENCE_INCOMPLETE` رد شود.
8. split کامل فقط برای ADR بازبینی‌شده eligible شود.

## ۸. نسخه‌بندی و بازگشت

تغییر مالک جدول، context یا envelope رویداد breaking است و major version، ADR و برنامه migration/reconciliation می‌خواهد. این Task فقط سند و validator است؛ rollback پیش از کدنویسی runtime با Git revert انجام می‌شود و هیچ تغییر سرور یا دیتابیس ندارد.
