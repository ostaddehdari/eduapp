# S05-W02 · Entitlement و feature flag

نسخهٔ قرارداد: `1.0.0`؛ شناسه الزام `FR-002`؛ مالک داده و سهمیه Billing، مالک تصمیم مجوز کاربر Access.

| قرارداد/رویداد | ورودی و خروجی | وضعیت انتشار |
| --- | --- | --- |
| `hasEntitlement({ tenantId, feature })` | تصمیم boolean از flag روشن، اشتراک فعال، grant معتبر و سهمیهٔ باقیمانده | فقط سرویس داخلی برای Access؛ endpoint عمومی ندارد |
| `check({ identity, feature, action })` | تصمیم boolean پس از مجوز مستقل کاربر و entitlement | فقط سرویس داخلی |
| `reserve({ identity, feature, action, requestKey, amount })` | `used`, `replayed`؛ افزایش اتمی شمارنده یا خطای مجوز/تعارض | فقط سرویس داخلی؛ `requestKey` UUID الزامی |
| `billing.subscription_activated.v1` | منبع اعطای grant پس از پرداخت verified | تولید و مصرف در ورک‌های پرداخت بعدی؛ در این ورک منتشر نمی‌شود |

| جدول | مالک و مرز داده |
| --- | --- |
| `commercial_billing.feature_flags` | مالک `eduapp_commercial_billing_owner`؛ نقش runtime فقط SELECT، پیش‌فرض خاموش |
| `commercial_billing.entitlements`, `subscriptions` | مالک Billing؛ تصمیم‌گیری با `eduapp_billing_api` در تراکنش tenant-aware؛ grant بدون اشتراک مبنا مردود. نقش Billing از migration پایه مجوز نوشتن هم دارد؛ تفکیک نقش پرداخت/خواندن پیش از فعال‌سازی production لازم است. |
| `commercial_billing.usage_counters`, `usage_requests` | مالک Billing؛ RLS اجباری با `tenant_id`، runtime فقط خواندن/درج و افزایش ستون `used` |

| وضعیت | مجوز Access | flag و grant Billing | نتیجه |
| --- | --- | --- | --- |
| کاربر مجاز و سهمیهٔ باقیمانده | بله | بله | اجازه و رزرو مصرف |
| کاربر بدون نقش یا scope معتبر | خیر | هر مقدار | منع |
| اشتراک غیرفعال، grant منقضی یا flag خاموش | هر مقدار | خیر | منع |
| سهمیه تمام‌شده | بله | grant معتبر | منع مصرف جدید؛ بازپخش همان `requestKey` مجاز |

خطاهای قرارداد: ورودی نامعتبر `INVALID_REQUEST`، بدون مجوز یا سهمیه `FORBIDDEN`، بازپخش ناسازگار `CONFLICT`. این قرارداد پولی یا مجوز کاربر را خودکار ایجاد نمی‌کند؛ تغییر ناسازگار در API یا رویداد نیازمند نسخهٔ جدید است.

مالک داده Billing در طرح `commercial_billing` است. سه تصمیم باید مستقل باشند: مجوز نقش و محدودهٔ کاربر توسط Access، فعال‌بودن feature flag توسط Billing، و entitlement معتبر ناشی از اشتراک فعال همان tenant توسط Billing. نبود هر کدام به معنای منع دسترسی است. `createEntitlementService().hasEntitlement` فقط تصمیم دوم و سوم را برای تزریق به `AccessService.hasEntitlement` ارائه می‌کند؛ `check` و `reserve` نیازمند تابع مستقل `authorizePermission` هستند.

نسخهٔ قرارداد `1.0.0`: `feature_flags(feature, enabled, revision)` در اختیار مالک Billing است و پیش‌فرض flag خاموش است. رکوردهای قدیمی `entitlements` بدون `source_subscription_id` دسترسی ایجاد نمی‌کنند. اعتبار هر grant به بازهٔ `valid_from` تا `valid_to`، وضعیت `active` اشتراک همان tenant و feature flag روشن وابسته است. `limit_value` سقف ماه UTC است؛ مقدار NULL یعنی سهمیه نامحدود. برای هر tenant و feature، جدیدترین grant معتبر ملاک است. تغییرات اشتراک و اعطای entitlement فقط در مسیر تأیید پرداخت ورک‌های بعدی S05 انجام می‌شود؛ این ورک API عمومی برای اعطا یا روشن کردن feature flag ارائه نمی‌کند.

رزرو مصرف با `request_key` UUID در `usage_requests` ثبت می‌شود. درخواست تکراری با همان مقدار بازپخش می‌شود؛ مقدار متفاوت تعارض است. شمارندهٔ ماهانه در تراکنش tenant-aware و قفل advisory به صورت اتمی افزایش می‌یابد. `usage_counters` و `usage_requests` دارای RLS اجباری‌اند؛ امکان دسترسی از tenant دیگر یا خواندن بدون زمینه وجود ندارد. مجوز اجرای مصرف باید جداگانه از نقش کاربر احراز شود.

Migration افزایشی `0014-feature-entitlements.sql` پس از `0013-plan-catalog` اجرا می‌شود. اجرای production و اعطای دادهٔ واقعی منوط به بررسی جداگانهٔ DB، پشتیبان و جریان پرداخت تأییدشده است.
